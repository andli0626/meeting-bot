# 标签与发布手册

本仓库使用 **Git 标签（Tag）** 标记版本，并基于标签在 GitLab 创建**发布（Release）**。下文以本次 `v1.0.0` 为例，给出完整操作流程，后续版本照此套用。

- **远端**：`http://192.168.0.200/lil/weeklymeetingbot.git`（自建 GitLab）
- **版本号规则**：语义化版本 `v<主版本>.<次版本>.<修订号>`（如 `v1.0.0`、`v1.6.0`）
- **标签类型**：使用 **annotated 标签**（`-a`），强制带发布说明，便于追溯
- **发布入口**：GitLab 的 Releases 页面，基于已推送的标签创建

---

## 一、打标签

### 1.1 打标签前检查

```bash
# 1. 切到要发布的分支（通常是 main）
git checkout main

# 2. 拉取最新，避免基于旧提交打标签
git pull origin main

# 3. 确认当前 HEAD 是你想要的发布基线
git log --oneline -1
# 期望输出示例：cfcf3bf docs: 新增项目 README，汇总安装、使用、配置与文档索引
```

> 注意：标签打在**提交**上，不是打在分支上。一定要先确认 `HEAD` 指向的提交就是你想要的 1.0.0 基线，否则标签会指到错误版本。

### 1.2 创建 annotated 标签

```bash
git tag -a v1.0.0 -m "release: 1.0.0 发布

- 一键创建部门周例会草稿
- 自动填写会议信息、按姓名选择参会/列席人员、新增议题
- 配置记忆、菜单命令、执行日志
- 新增项目 README 文档"
```

**参数说明**：

- `-a v1.0.0`：创建 annotated 标签，名字为 `v1.0.0`
- `-m "..."`：标签附注（发布说明），支持多行；**不要用轻量标签**（不带 `-a`），因为轻量标签无法在 GitLab 发布里携带说明

### 1.3 验证标签

```bash
# 查看本地标签列表及附注
git tag -l -n1
# 期望输出：v1.0.0          release: 1.0.0 发布

# 查看标签完整信息（含作者、日期、说明）
git show v1.0.0
```

### 1.4 推送标签到远端

```bash
# 推送单个标签
git push origin v1.0.0
```

> **不要**用 `git push --tags` 一次性推送所有标签，会把本地未审核的标签也推上去。发版只推**当前版本**那一个。

推送成功后，可在 http://192.168.0.200/lil/weeklymeetingbot/-/tags 看到 `v1.0.0`。

## 二、创建发布

标签推上去后，有两种方式创建 GitLab 发布。

### 2.1 方式 A：从发布页面创建（推荐）

1. 打开下面任一地址：
   - 直接带 tag 参数（推荐）：http://192.168.0.200/lil/weeklymeetingbot/-/releases/new?tag=v1.0.0
   - 或从标签页进入：http://192.168.0.200/lil/weeklymeetingbot/-/tags → 找到 `v1.0.0` → 点「创建发布」
2. 页面会自动关联 `v1.0.0` 标签
3. 填写**发布标题**（如 `v1.0.0`）与**发布说明**（Markdown）
4. 点「创建发布」提交

### 2.2 方式 B：从标签详情页创建

1. 打开 http://192.168.0.200/lil/weeklymeetingbot/-/tags/v1.0.0
2. 点页面上的「**New release**」或「创建发布」
3. 填写标题与说明后提交

### 2.3 发布说明模板

```markdown
## v1.0.0

### 新功能

- 一键创建部门周例会草稿
- 自动填写会议信息、按姓名选择参会/列席人员、新增议题
- 配置记忆、菜单命令、执行日志
- 新增项目 README 文档

### 修复

- （列出本次修复，没有则删除本节）

### 升级说明

- （列出不兼容变更或迁移步骤，没有则删除本节）
```

## 三、常见操作

### 3.1 查看已有标签与发布

```bash
# 本地标签
git tag -l -n1

# 标签对应提交
git show v1.0.0
```

页面查看：http://192.168.0.200/lil/weeklymeetingbot/-/tags

### 3.2 修改标签（发版前发现说明写错时）

```bash
# 1. 本地强制替换标签（附注改写）
git tag -a -f v1.0.0 -m "release: 1.0.0 发布

- 修正后的发布说明"

# 2. 强制推送到远端覆盖
git push -f origin v1.0.0
```

> 强制覆盖标签是**破坏性操作**。仅在**还没创建 GitLab 发布**、或**已协商一致**时使用；已对外发布的版本严禁移动标签。

### 3.3 删除标签（发版失误时）

```bash
# 删除本地标签
git tag -d v1.0.0

# 删除远端标签
git push origin :refs/tags/v1.0.0
```

> 删除后需到 GitLab 同步删除对应的 Release（如有）。

### 3.4 基于发布分支发版（可选）

如需在发版前冻结代码、做最后验证，可用发布分支：

```bash
# 从 main 创建发布分支
git checkout -b release/1.0.0
git push -u origin release/1.0.0

# 在 release 上做最后验证、修 bug（修后合并回 main）
# 确认无误后，在 release 分支 HEAD 打标签
git tag -a v1.0.0 -m "release: 1.0.0 ..."
git push origin v1.0.0
```

发布分支命名：`release/<版本号>`，如 `release/1.0.0`、`release/1.6.0`。

## 四、版本号约定

遵循[语义化版本 2.0.0](https://semver.org/)：

| 版本位             | 何时递增                | 举例                             |
| ------------------ | ----------------------- | -------------------------------- |
| **主版本** `X.0.0` | 不兼容的 API / 行为变更 | 会议创建流程彻底重写             |
| **次版本** `1.X.0` | 向下兼容的新功能        | 新增「诊断会议表单」菜单         |
| **修订号** `1.0.X` | 向下兼容的问题修复      | 修复人员 GUID 缺失导致的写入失败 |

本仓库脚本版本号写在 `oa-weekly-meeting.user.js` 文件头的 `@version` 字段，**Git 标签版本号应与脚本 `@version` 一致**。发版前请先更新脚本内的版本号。

## 五、完整发版清单（Checklist）

发版时按下列顺序逐项打勾：

- [ ] 1. 代码已合并到 `main`，`git pull origin main` 为最新
- [ ] 2. `oa-weekly-meeting.user.js` 文件头 `@version` 已更新为目标版本（如 `1.0.0`）
- [ ] 3. 提交并推送版本号改动：`git commit -m "chore: 发布脚本 v1.0.0"` && `git push`
- [ ] 4. 确认 `main` 的 `HEAD` 为预期基线：`git log --oneline -1`
- [ ] 5. 打 annotated 标签：`git tag -a v1.0.0 -m "release: 1.0.0 ..."`
- [ ] 6. 推送标签：`git push origin v1.0.0`
- [ ] 7. 到 http://192.168.0.200/lil/weeklymeetingbot/-/releases/new?tag=v1.0.0 创建发布
- [ ] 8. 核对发布内容（标题、说明、关联标签）无误后提交
